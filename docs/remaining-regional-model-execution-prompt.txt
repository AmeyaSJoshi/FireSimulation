3. NON-NEGOTIABLE TRUTH AND SAFETY RULES
-----------------------------------------

- Do not call this an operational tool, emergency system, forecast, or validated real-time predictor.

- Never label a run regional/active unless valid direct FBFM40 cells arrived, passed dimension/bounds/orientation/nodata validation, and meet a declared valid-cell coverage threshold.
- Do not tune and evaluate on the same fires.
- Do not modify an evaluator, metric definition, perimeter geometry, validation mask, timestep, or fixture solely to improve scores.
- Do not infer suppression from a stalled observed perimeter and call the result natural fire behavior.
- Do not label ensemble quantiles as probabilities until coverage has been tested against held-out fires.
- Preserve zero-crossing water barriers, non-burnable barriers, finite termination, deterministic seeds, and provenance metadata.
- Any approximation must be named in code, docs, UI metadata, and tests.

4. DEFINITION OF DONE
----------------------

The work is complete only when all applicable gates pass and the final report lists every remaining failure. A feature can be marked experimental when its production gate is not met, but it cannot be presented as complete.

Required completion gates:

A. Regional input contract

- A deterministic mocked integration test proves a valid asymmetric FBFM40 raster travels from response parsing through grid alignment, per-cell fuel selection, propagation, metrics, and provenance.
- Tests cover raw code mapping, nodata, malformed/empty payloads, HTTP failures, timeout/retry budget, response dimensions, requested bounds, CRS/geotransform assumptions, pixel orientation, north/south row order, and resampling.
- An asymmetric sentinel raster proves that values do not appear in mirrored, transposed, or vertically flipped cells.
- Live transport is probed when available, but a live failure produces an explicit fallback/unavailable state. It is never hidden.
- Valid-cell fraction, source URL, product/version, acquisition timestamp, resolution, bbox, hash/cache identity, fallback reason, and model-definition version are recorded.

B. Physical invariants

- Existing Rothermel, independent-rate, WAF, convergence, water, lifecycle, and determinism validators continue to pass.
- Water and non-burnable cells always have zero spread and no directed path crosses a water edge, including diagonal, sub-cell, coastal, river, and lake cases.
- Fire reaches a finite terminal state. Burnout must be more than only a rendering effect; either enforce source energy/residence constraints in propagation or document and test the exact front-arrival approximation without calling it a complete consumption model.
- Weather validity is explicit. A historical weather timeline must not silently persist its final observation forever. Post-window behavior must be blocked, flagged, or use a documented forecast policy.
- Same inputs, model version, source manifest, and seed produce repeatable results.

C. Multi-fire evaluation

- Preserve the existing two-case baseline.
- Expand to at least six independent U.S. fires for the hackathon track; eight or more is preferred if reliable public inputs can be frozen.
- Stratify cases across regions and regimes: at minimum grass, shrub, timber/mixed fuel, steep terrain, flat terrain, and a water-adjacent/coastal case. Include a geographically or temporally held-out region/year.
- Freeze ignition coordinates/time, observation times, perimeters, weather source and window, terrain source, fuel source, grid/resolution, suppression assumptions, random seed, and model version.
- Use a calibration set and an untouched holdout set. Prefer four calibration fires plus two or more holdouts. Never rank parameters on holdouts.
- Report per fire and aggregate: IoU, F1, precision, recall, predicted/observed area ratio, centroid error, boundary distance/error, arrival/timing error when available, field-boundary truncation, termination reason, and all input provenance.
- Report worst case and medians, not only means.

D. Calibration discipline

- Calibrate only interpretable, source-supported quantities: moisture initialization/lag, fuel availability within defensible bounds, wind adjustment/shelter, live-fuel parameters, ignition uncertainty, and spotting parameters after spotting exists.
- Keep Rothermel constants, water barriers, evaluator definitions, and numerical timestep out of calibration.
- Every trial has a complete manifest containing parameters, seed, source hashes, code/model version, split, metrics, and status.
- Accept a default change only when aggregate holdout performance is no worse than the frozen baseline, median per-fire IoU improves meaningfully, no holdout regresses materially, and no critical regime fails. If evidence is weaker, keep it experimental.

E. Product honesty

- UI and reports show the actual active fuel source, fallback state, coverage, resolution, weather provenance/validity, terrain provenance, moisture basis, model version, seed, uncertainty basis, and benchmark status.
- Uncalibrated ranges say "scenario range" or equivalent, not probability/confidence interval.
- The app retains a clear educational disclaimer and a visible distinction between active regional inputs, fallback inputs, and exploratory global behavior.

12. CLAUDE FOLLOW-UP -- ROOT-CAUSED AND FIXED THE GEOMETRY GATE
-------------------------------------------------------------------

Date: 2026-07-24 (same day, later in session)
Agent: Claude Code

Section 11 documented a real live LANDFIRE response being rejected by
`validateLandfireFuelRasterGeometry`, deliberately left unfixed pending
more evidence. This section reports that fix.

Followed systematic root-cause debugging rather than loosening the
tolerance blindly: fetched 3 MORE real samples from the live WCS endpoint
at different CONUS locations and request sizes (bbox -105,39/-104.9,39.1
width 64; -120,37/-119.9,37.1 width 64; -110,35/-109.5,35.5 width 128;
-95,32/-94.95,32.05 width 32). All 4 real samples (including the one from
section 11) showed the SAME two real causes:

1. Live GeoServer WCS 1.0.0 legitimately pads/resamples the returned
   extent to its native grid rather than matching the request exactly.
   Resolution came back up to ~1.6x coarser than requested per axis;
   width/height in pixels were always honored exactly.

2. `geotiff.js` (this project's exact installed version, see
   node_modules/geotiff/dist-node/geotiffimage.js `getResolution()`)
   returns a NEGATIVE y-resolution for GeoTIFFs encoded with
   ModelPixelScale, but a POSITIVE y-resolution for GeoTIFFs encoded with
   ModelTransformation -- for the SAME physical north-up orientation. The

Step 3 -- Real terrain exposed a genuine, previously-latent physics bug,
root-caused and fixed at the source:

With real (non-flat) terrain in place, `npm test` started failing:
`RangeError: fireEllipse: backingRateMPerMin must not exceed
headRateMPerMin, got 0.058398471989792214` inside
`ellipseEccentricity` (`src/lib/fireEllipse.js`). Followed
systematic-debugging rather than patching the assertion: added a
temporary debug print to capture the actual head/backing values
(0.05706671196617654 vs 0.058398471989792214, an ~2.3% inversion --
confirmed NOT a floating-point tie, a real gap).

Traced it to `src/lib/surfaceSpread.js`: the combined wind+slope
"forcing direction" used to pick which candidate direction gets labeled
`head` is a linear vector sum of the two component forces, but
`calculateWindFactor`'s response to alignment is sub-linear
(`alignment ** exponentB`, exponentB < 1) while
`calculateSlopeFactor`'s is quadratic (`alignment ** 2`). When wind and
slope point in different directions, that mismatch can make the
heuristic's chosen direction a genuine ~2% slower than its exact
opposite -- violating the ellipse transform's required
head-is-the-maximum invariant (Andrews 2018). This was structurally
impossible to hit before: with flat terrain, `slopeRadians` was always
exactly 0 everywhere, so `calculateSlopeFactor` always short-circuited
to a constant 0 and the wind/slope interaction never existed. All 342
prior tests always ran on flat terrain.

Fixed at the computation source in `surfaceSpread.js`, not by loosening
the `fireEllipse.js` assertion: now computes both the forcing-direction
rate and its exact opposite, and labels whichever is larger as `head`.
No Rothermel/wind/slope formula changed -- only which of the two
already-computed candidate directions receives the head label. Removed
the temporary debug print before finishing.
