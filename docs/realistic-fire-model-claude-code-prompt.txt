1. CURRENT PRODUCT CONTEXT
======================================================================

The app is a free browser-based Three.js/Vite application with:

- A textured global Earth rendered by Three.js.
- Direct click-to-ignite behavior on confirmed land.
- Ocean rejection based on the visible Earth texture.
- A Web Worker that currently runs a deterministic 128 x 128 cellular fire model.
- One kilometer cells and a 128 km simulation field.
- One model minute per simulation step.
- Open-Meteo elevation requests backed by Copernicus GLO-90.
- Terrain caching and explicit synthetic fallback states.
- Fuel, wind, moisture, slope, metrics, interpretation, local run history, and replay.
- Node test runner tests and a Vite production build.

Read all files in `src/`, `index.html`, `package.json`, `docs/`, and the recent git diff before changing code. Do not discard existing user changes. Preserve the current click-to-ignite workflow, Scenario Lab history/replay, worker isolation, and educational disclaimer.

2. NON-NEGOTIABLE TRUTH RULES
======================================================================

1. Do not call the result a forecast, operational prediction, emergency tool, or validated real-time model.
2. Do not use an LLM, neural network, or opaque learned multiplier as the fire-spread engine. The core must be deterministic, equation-based, and inspectable.
3. Do not invent values when an external dataset is missing. Every fallback must be visible in metadata and must lower the confidence label.
4. Do not imply 90 m or 1 km precision when the fuel, weather, or terrain inputs do not support it.
5. Do not copy equations from memory. Read and cite the primary technical sources, translate every equation into explicit units, and test dimensional behavior.
6. Do not silently mix coordinate systems, wind-direction conventions, raster axes, vertical datums, or cell-center/cell-edge interpretations.
7. Do not add crown fire, spotting, ember transport, suppression, smoke, or fire-atmosphere coupling until the surface-spread core passes its validation gates.
8. Do not add a new dependency, delete files, change the database/schema, or replace the existing model wholesale without stopping and asking for approval.
9. Keep the existing model behind a feature flag as a fallback until the new model passes all gates.
10. If evidence is insufficient to claim a feature is realistic, implement the feature as experimental and say exactly what is missing.

3. RECOMMENDED MODEL ARCHITECTURE
======================================================================

Create clean deterministic boundaries. The recommended pipeline is:

click location
  -> land/ocean and coverage validation
  -> local spatial domain definition
  -> terrain, land-cover/fuel, and weather acquisition
  -> raster normalization and common-grid alignment
  -> slope/aspect and fuel-parameter derivation
  -> local surface rate-of-spread kernel
  -> directional spatial propagation
  -> fuel burnout and fireline metrics
  -> ensemble uncertainty and interpretation

Use separate modules for these concerns. Do not put equations, network requests, raster alignment, worker messaging, and UI copy in one large function.

Recommended module boundaries:

- `src/lib/spatialGrid.js`
  - WGS84 click to local tangent-plane conversion.
  - Explicit grid origin, cell centers, cell size, field extent, row/column convention, and longitude wrapping.
  - Round-trip tests and antimeridian/high-latitude tests.

- `src/lib/terrainDerivatives.js`
  - Elevation validation.
  - Slope magnitude and aspect from finite differences in meters.
  - Explicit aspect convention and upslope vector.
  - No-data propagation; never turn missing elevation into a measured zero.

- `src/lib/fuelModels.js`
  - A versioned, testable mapping from land-cover classes to fire-behavior fuel models.
  - Fuel parameters by size class, including dead/live load, surface-area-to-volume ratio, heat content, mineral content, and extinction moisture.
  - Explicit confidence and source for every mapping.

- `src/lib/weatherInputs.js`
  - Wind speed/direction, air temperature, relative humidity/dew point, precipitation history if available, and timestamp.
  - Unit conversion and wind-direction convention in one place.
  - Distinguish 10 m or 20 ft observed/model wind from midflame wind.
  - Timestamp, source, resolution, and stale-data status.

- `src/lib/surfaceSpread.js`
  - Pure equation-based local surface fire behavior.
  - Returns rate in SI units first, then presentation conversions.
  - No DOM, network, randomness, or Three.js imports.

- `src/lib/firePropagation.js`
  - Deterministic directional propagation over the common raster.
  - Uses the local spread kernel rather than neighbor probability multipliers.
  - Handles arrival time, active front, burnout, and boundaries.

- `src/lib/uncertainty.js`
  - Seeded perturbations of uncertain weather, fuel mapping, and model parameters.
  - Returns quantiles/ranges, not uncalibrated probabilities.

- `src/workers/fireWorker.js`
  - Owns simulation stepping and ensemble execution.
  - Main thread receives compact frames and metrics only.

4. LOCATION-DEPENDENT DATA CONTRACT
======================================================================

For every click, construct a versioned scenario input object containing:

- WGS84 latitude and longitude.
- Local tangent-plane origin and orientation.
- Grid width, height, cell size, field extent, and simulation timestep.
- Elevation source, timestamp, vertical datum if known, and no-data mask.
- Derived slope magnitude and aspect per cell.
- Land-cover source, date, class, and confidence.
- Fuel-model code and all numerical fuel parameters per cell.
- Weather source, timestamp, forecast/analysis distinction, and all units.
- Wind measurement height and midflame adjustment method.
- Moisture source or explicitly labeled scenario assumption.
- Model version, feature flag, seed, and uncertainty configuration.

All raster fields must be aligned to the exact same grid. Test:

- Cell centers versus cell edges.
- North-up versus south-up rows.
- Longitude wrapping at +/-180 degrees.
- Polar latitude bounds.
- Terrain and fire overlay alignment.
- Land-mask and fuel-grid alignment.

The simulation must still ignite confirmed land when optional data are unavailable, but the UI must say which inputs are missing and must lower the quality/confidence label. Ocean clicks must never request fire terrain or start a worker run.

5. TERRAIN AND DERIVATIVES
======================================================================

Keep Copernicus GLO-90 via Open-Meteo as the free global terrain fallback. Treat it as coarse global elevation, not building-scale or tactical terrain.

Derive slope from rise/run in meters, not from arbitrary normalized texture values. Derive aspect as a vector pointing uphill. Use the vector directly in the spread calculation. Document:

- DEM sample spacing.
- Interpolation method.
- Edge behavior.
- No-data behavior.
- Whether heights are surface-model or bare-earth values.

Tests must include flat terrain, constant planar slopes pointing in each cardinal direction, sharp ridges, missing cells, and antimeridian windows. The slope of flat terrain must be exactly zero within tolerance. A missing DEM must not look identical to a measured flat DEM in metadata.

6. FUEL MODELING
======================================================================

Use recognized fire-behavior fuel-model concepts instead of the current three arbitrary presets.

Start with surface fuels only. Build a small versioned table of parameters with citations. Include, where the selected model requires them:

- Fuel load by size class.
- Live and dead fuel components.
- Surface-area-to-volume ratio.
- Fuel-bed depth.
- Fuel particle density.
- Heat content.
- Mineral content and effective mineral content.
- Moisture of extinction.
- Canopy/shelter information if used for wind adjustment.

LANDFIRE fire-behavior fuel models are a strong US source, but they do not provide global coverage. Do not label a US-only mapping as global. For non-US locations, use a documented global land-cover source and a conservative, explicitly low-confidence crosswalk only if its licensing and semantics are clear. Otherwise use a generic experimental fuel class and label it as such.

Tests must prove that:

- Higher fuel load does not reduce spread when all else is equal unless the documented equation says so.
- Wet fuel reduces spread.
- Fuel models produce different but bounded behavior.
- Missing fuel parameters trigger an explicit low-confidence path.
- Non-burnable classes create a true barrier or non-burnable cell.

7. WEATHER AND MOISTURE
======================================================================

Use free public weather only with source, timestamp, units, and stale-data metadata. Open-Meteo can provide temperature, relative humidity, dew point, precipitation, wind speed, wind direction, wind gusts, and soil moisture variables; verify current API details before implementation.

Do not pass raw 10 m wind directly into a surface model without documenting the conversion. Implement a named wind-adjustment function that distinguishes:

- Input measurement height.
- Canopy/fuel shelter assumptions.
- Midflame wind output.
- Calm-wind behavior.
- Direction convention and vector conversion.

Moisture must be modeled by the fuel classes the spread equation expects. If only humidity or a scenario percentage is available, label it as an estimate and do not pretend it is measured fuel moisture. Handle precipitation history conservatively.

Tests must cover unit conversions, calm wind, direction wrapping, missing weather, stale weather, wind gust versus sustained wind, and moisture bounds.

======================================================================
8. SURFACE-SPREAD EQUATIONS
======================================================================

Implement a documented Rothermel-style surface-spread core as the first realistic physics milestone. Read the original Rothermel paper and a current US Forest Service explanation before coding.

The pure function should accept validated fuel parameters, fuel moisture, midflame wind, slope/aspect, and atmospheric assumptions and return:

- No-wind/no-slope spread rate.
- Effective wind/slope vector.
- Head, flank, and backing spread rates where supported.
- Directional rate for an arbitrary travel direction.
- Fireline intensity and heat output if the required inputs are available.
- Domain/quality flags and warnings.

Use SI units internally. Make every conversion explicit. Reject or clamp out-of-domain values with a warning; never let NaN or Infinity enter the propagation engine.

Do not hide unsupported terms behind one generic multiplier. If a term is approximated, name the approximation in code, docs, metadata, and tests.

The implementation must prove these directional properties with controlled tests:

- Flat terrain and zero wind are approximately isotropic.
- Head-fire spread is greater than flank spread when wind is present.
- Backing spread is positive but lower when the model supports backing fire.
- Upslope spread is greater than downslope spread for the same fuel and wind.
- Higher moisture lowers spread within the valid domain.
- Non-burnable fuel produces zero spread.
- Reversing wind direction reverses the directional bias.

======================================================================
9. SPATIAL PROPAGATION AND NUMERICAL STABILITY
======================================================================

Do not simply increase the current neighbor ignition probability. Use the local physical rate to determine travel time between cells.

Choose and document one deterministic propagation method:

- A priority-queue arrival-time solver over the raster, or
- A fast-marching/eikonal-style solver, or
- A substepped Huygens/front-propagation method with a documented stability bound.

Prefer the simplest method that preserves directional rates and is stable at the current 128 x 128 resolution. The method must:

- Respect cell size and units.
- Use a stable timestep based on the maximum local spread rate.
- Prevent cells from jumping across multiple unsupported cells in one step.
- Handle non-burnable cells and field boundaries explicitly.
- Avoid diagonal shortcuts that violate the chosen distance metric.
- Produce deterministic results for the same seed and inputs.
- Stop cleanly when the front has no active burnable cells.

Add convergence checks: a smaller timestep should produce a bounded difference in arrival time and perimeter compared with the baseline. Record the numerical tolerance and explain why it is acceptable at the chosen resolution.

10. FIRE LIFECYCLE
======================================================================

Model at least these states explicitly:

- Ignition/heating.
- Flaming combustion.
- Burnout/residence time based on fuel and energy.
- Burned/non-burnable.

Do not allow burned cells to reignite unless a future spotting feature explicitly introduces a new ember source. Keep ignition energy, burn duration, and state transitions deterministic.

Defer crown fire, spotting, ember transport, and smoke until the surface model passes all earlier tests. When those features are eventually added, they must be separate validated modules, not hidden effects in the surface rate.

11. UNCERTAINTY AND INTERPRETATION
======================================================================

A single deterministic perimeter is not a probability forecast. Add an optional seeded ensemble only after the deterministic run is correct.

Perturb only documented uncertain inputs, such as:

- Weather within a stated range.
- Fuel-model crosswalk choices.
- Moisture estimates.
- Selected model parameters within defensible bounds.

Return median, low/high quantiles, and data-quality flags. Do not label an ensemble quantile as a calibrated probability unless validation supports that interpretation.

The UI must show:

- Model version and feature flag.
- Data sources and timestamps.
- Spatial and temporal resolution.
- Input quality/confidence.
- Which inputs were measured, modeled, estimated, or synthetic.
- Deterministic seed and ensemble configuration.
- A visible "educational simulation, not a forecast" warning.
- A limitation message whenever global fuel/weather coverage is incomplete.

Avoid false precision. Round outputs to a precision supported by the coarsest input and label rates in clear units.

15. DEFINITION OF DONE
======================================================================

Do not claim the model is realistic merely because the fire looks more convincing.

The realism upgrade is complete only when:

- The equation-based spread core is isolated, cited, unit-tested, and numerically bounded.
- Location-dependent terrain, fuel, and weather inputs are aligned and provenance-aware.
- Missing or low-quality inputs are visible and reduce confidence.
- Propagation is rate-based and stable, not a tuned neighbor probability.
- Identical saved scenarios reproduce identical results.
- Wind, slope, fuel, and moisture produce directionally explainable effects.
- A worker benchmark demonstrates acceptable browser performance.
- Validation results, limitations, and unsupported regions are documented.
- Existing click-to-ignite, ocean protection, history/replay, metrics, build, and tests still work.
- The UI clearly says the output is educational and not an operational forecast.

If any of these are not true, report the exact gap and leave the feature behind a clearly labeled experimental flag. Do not paper over the gap with extra visual effects, arbitrary coefficients, or a neural network.
